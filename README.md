# Редакционная аналитика DEMO

Внутренний дашборд для рассылок ГФ и ГЗ.

С 4 сентября 2026 года проект работает по новой архитектуре и **не использует старую таблицу редакционной DEMO-аналитики как источник данных**.

## Источники истины

У сайта два исходных источника:

1. **Фактические отчёты Sendsay** из подключённой папки Google Drive.
   - поддерживаются `.webarchive`, `.mhtml`, `.mht`;
   - факт отправки, subject, дата/время, Campaign ID, открытия и клики берутся только из Sendsay;
   - повторные сохранения одной отправки дедуплицируются по `Campaign ID`.

2. **Исходная Google-таблица «Статистика по ДЕМО»**.
   - из неё берутся R / Y / G и недельные планы;
   - конкретному письму R / Y / G назначаются только при точном совпадении Campaign / UTM;
   - общий план-факт строится заново по шести продуктам.

Служебная таблица `Analytics Center — служебные данные v2` является только техническим хранилищем сайта.

## Торговые письма (Market / Project / Event)

Раздел **«Торговые письма»** независим от вкладок «Письма», «Новости» и АКТИВДЕМО:

- **ГФ** и **ГЗ** выбираются отдельным фильтром;
- письма отбираются строго по фактическим меткам выпуска в Sendsay: Market, Project, Event (поля API issue.label0–issue.label9);
- показываются тема, Campaign, дата, доставлено, OR, CTR, CTOR, статистика по меткам и ссылка на выпуск;
- если в одном выпуске несколько нужных меток, он считается **один раз**;
- данные сохраняются в отдельный технический лист «_Торговые письма», не участвуют в DEMO R/Y/G, планах и редакционном дожиме.

В отличие от существующего импорта отчётов DEMO через сохранённые .webarchive, метки Sendsay **не содержатся надёжно в этих файлах**. Поэтому для торговых писем используется серверный запрос stat.uni по настоящим меткам. Данные не берутся из похожих слов в Campaign или теме.

### Первичная настройка Sendsay API

API-ключи не помещать в репозиторий, HTML, таблицы или параметры URL. В настройках **того Apps Script проекта, который исполняет Web App**, открыть «Настройки проекта → Свойства скрипта» и добавить:

| Свойство | Значение |
| --- | --- |
| SENDSAY_TRADE_GF_ACCOUNT | Код аккаунта Sendsay для Госфинансов |
| SENDSAY_TRADE_GF_APIKEY | API-ключ этого аккаунта, с правом чтения статистики |
| SENDSAY_TRADE_GZ_ACCOUNT | Код аккаунта Sendsay для Госзаказа |
| SENDSAY_TRADE_GZ_APIKEY | API-ключ этого аккаунта, с правом чтения статистики |
| SENDSAY_TRADE_SINCE | Необязательно: дата начала YYYY-MM-DD, по умолчанию 2026-01-01 |

Для API-контроля лучше использовать отдельного пользователя с минимальными правами на чтение. Если настройки внесены только для ГФ или только для ГЗ, синхронизация сможет загрузить это направление и явно покажет, что второе не подключено.

**Важно:** при указании одинакового кода аккаунта для ГФ и ГЗ синхронизация останавливается. Иначе все выпуски одного аккаунта ошибочно попадут в оба направления. Для общего аккаунта понадобится уточнить отдельный стабильный признак ГФ/ГЗ (например, поле выпуска) до подключения.

### Синхронизация и публикация

1. Добавить файл TradeEmails.gs в действующий проект Apps Script, а обновлённый index.html заменить целиком.
2. Сохранить свойства скрипта; повторный запуск setup() не требуется.
3. Создать новую версию развертывания **Apps Script Web App**.
4. Открыть «Торговые письма» → **«Синхронизировать с Sendsay»**. Кнопка считывает выпуски порциями по 150 до завершения обоих аккаунтов, дедуплицирует по аккаунту и ID выпуска; устаревшие строки удаляет только по итогам успешного полного прохода.
5. Проверить три метки и оба направления на конкретных отправках в Sendsay.

Код уже использует OAuth scope script.external_request из appsscript.json. В GitHub Pages доступен **только интерфейс** с демо-данными: реальная загрузка работает в развернутом Apps Script Web App. Публикация на GitHub **не обновляет автоматически** код Apps Script и не даёт сайту доступа к API-ключам.

## Каноническое правило NEWS

Новостными считаются **только** два штатных типа Campaign:

- ГФ: `Gosfinansi_letter_news_GF_digest...` из файлов вида `265 | NEWS | Gosfinansi_letter_news_GF_digest...`;
- ГЗ: `letter_news_goszakaz_regular_news_digest...` из файлов вида `729 | News | letter_news_goszakaz_regular_news_digest...`.

`_nd_`, случайное слово `news`, любой другой `digest` и похожие маркеры сами по себе NEWS не делают.

## Главные правила аналитики

- KPI = только Green.
- Yellow = потенциал для дожима.
- Red = диагностический слой, но не выполненный результат.
- Периодика и Системы дозревают около 3 дней.
- Школы дозревают около 6 дней.
- Green всегда исключается из дожима.
- Сначала Yellow, затем при необходимости активные Red.
- Exact-материал и очень близкий сюжет не повторяются в пределах 7 дней.
- Открытия, клики и клики после открытия оцениваются отдельно от Green.

## Синхронизация

Кнопка **«Синхронизировать всё»** не имеет искусственного лимита на общее число файлов. Сервер обрабатывает файлы небольшими пакетами, а браузер продолжает вызывать синхронизацию до `remaining = 0`. Пакет нужен только для защиты от таймаута Apps Script, а не как общий лимит.

Ручная загрузка также не ограничена нашим числом файлов и не имеет нашего отдельного лимита размера. Остаются только технические ограничения самой платформы Google Apps Script / браузера.

Ошибочные файлы можно повторно обработать при полной синхронизации.

## Статус импорта

В служебном разделе отдельно показываются:

- **Файлов загружено** — все текущие сохранённые файлы, включая дубли и ошибки;
- **Уникальных отправок** — канонические Sendsay Campaign ID;
- ошибки;
- дубли;
- DEMO связано;
- без связи;
- удалено;
- последняя дата отправки и время последнего импорта.

Поэтому загрузка нового дубля теперь видна как новый файл, даже если число уникальных отправок не изменилось.

## Публикация

После первого перехода на v2:

1. Один раз запустить `setup()`.
2. Подключить папку Sendsay в разделе «Служебное».
3. Нажать «Синхронизировать всё».
4. Проверить W36: 260 / 464.
5. Проверить последнюю дату отправки и новые файлы.
6. Развернуть новую версию Web App.

`setup()` при каждом обновлении запускать не нужно.
