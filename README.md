# Редакционная аналитика DEMO

Внутренний дашборд для рассылок ГФ и ГЗ.

С 4 сентября 2026 года проект работает по новой архитектуре и **не использует старую таблицу «DEMO-рассылки ГФ и ГЗ — редакционная аналитика» как источник данных**.

## Источники истины

У сайта только два исходных источника.

1. **Фактические отчёты Sendsay** из подключённой папки Google Drive.
   - поддерживаются `.webarchive`, `.mhtml`, `.mht`;
   - факт отправки берётся только из Sendsay;
   - из отчёта читаются дата и время отправки, Campaign ID, Campaign, subject, доставлено, открытия, клики, клики после открытия и другие показатели верхней воронки;
   - повторно загруженные версии не должны создавать второе письмо: каноническая версия определяется по `Campaign ID`.

2. **Исходная Google-таблица «Статистика по ДЕМО»**.
   - из неё берутся R / Y / G и недельные планы;
   - общий план-факт строится заново из исходных продуктовых листов;
   - конкретному письму R / Y / G назначаются только при точном совпадении `Campaign` / UTM;
   - новостным письмам R / Y / G не приписываются без точной UTM-привязки.

Служебная таблица `Analytics Center — служебные данные v2` создаётся автоматически функцией `setup()` и используется только как технический кэш сайта. Это **не источник аналитики**.

## Актуальные правила аналитики

- KPI = только **Green**.
- Yellow = потенциал и база для первичного дожима.
- Red = диагностический слой, а не выполненный результат.
- Периодика и Системы дозревают примерно 3 дня.
- Школы дозревают примерно 6 дней.
- Green всегда исключаем из дожима.
- Сначала работаем с Yellow, затем при необходимости с активными Red.
- Exact-материал и очень близкий сюжет не повторяем в пределах 7 дней.
- Открытия / клики / клики после открытия оцениваются отдельно от downstream-конверсии в Green.
- Плановая тема не считается фактически отправленным письмом, пока нет отчёта Sendsay.

## Что уже работает

- план-факт и R / Y / G по шести продуктам;
- динамика по неделям;
- реестр фактически отправленных писем;
- `.webarchive` из Safari / macOS и `.mhtml/.mht`;
- сортировка и фильтры по письмам;
- отдельная аналитика Дожима DEMO;
- дедупликация фактических отправок по `Campaign ID`;
- точная связь письма с DEMO по Campaign;
- список ошибок импорта и дублей;
- автоматическое исключение удалённых из исходной папки файлов из актуального реестра;
- решения по дожиму с учётом Green / Yellow / плана;
- ручная загрузка по схеме **сначала сохранить в Drive → затем единый папочный импорт**;
- повторная попытка ранее ошибочных файлов при запуске надёжной синхронизации;
- «Синхронизировать всё» больше не ограничено 100 файлами на одно нажатие;
- единая финальная классификация обычных DEMO / Дожима DEMO / новостных писем в `mail_classification_ui.html`.

## Важный фикс планов

В листе `Планы на год` значения плана могут совпадать с номерами недель, например `43` или `46`. Поэтому старый алгоритм мог принять строку `План` за строку с номерами недель и получить нулевой план по части продуктов.

Файл `zz_plan_fix.gs` содержит актуальный фикс этой ошибки. Он обязателен для Apps Script вместе с `Code.gs`.

Для W36 исходный расчёт должен давать **260 Green из плана 464**.

Исправлено:

- ошибка разбора теперь остаётся видимой в `_Sendsay v2`, а файл остаётся в Drive;

- полная синхронизация идёт до конца очереди, а не максимум 25 пакетов по 4 файла;
- служебный `_nd_` больше не используется как самостоятельный признак новостного письма;
- финальная UI-классификация опирается на серверный `type=news` или явный `letter_news/news/digest`, а Дожим DEMO определяется отдельно;
- редакционные подписи OR / CTR / CTOR переводятся на понятный русский язык отдельным последним UI-модулем.

Остаются два архитектурных долга, которые нужно убрать при следующем объединении серверного файла:
1. `Code.gs` и `zz_calls_ui.gs` оба содержат `doGet()`. Текущая сборка использует позднее переопределение из `zz_calls_ui.gs`, но в финальной чистой версии должен остаться один серверный вход.
2. Исправленный `readDemoPlans_` пока живёт в `zz_plan_fix.gs` как переопределение функции из `Code.gs`. В финальной чистой версии фикс нужно встроить прямо в `Code.gs` и удалить временное переопределение.

Эти два долга не возвращают зависимость от старой DEMO-аналитики, но делают проект зависимым от порядка загрузки файлов Apps Script, поэтому их нельзя считать желательным постоянным состоянием.

## Публикация в Google Apps Script

В Apps Script должны быть перенесены **все серверные `.gs` и подключаемые `.html` файлы, которые используются текущей версией**, а не только один `Code.gs`.

Для текущей сборки нужны:
- `Code.gs`;
- `SendsayUpload.gs`;
- `zz_plan_fix.gs`;
- `zz_calls_ui.gs`;
- `Calls.gs`;
- `index.html`;
- `compat_ui.html`;
- `calls_ui.html`;
- `sendsay_ui.html`;
- `email_analytics_ui.html`;
- `news_ui.html`;
- `runtime_fixes_ui.html`;
- `final_polish_ui.html`;
- `mail_classification_ui.html`;
- `russian_metrics_ui.html`;
- `appsscript.json`.

После первого перехода на v2:
1. Запустить `setup()` один раз.
2. Подтвердить доступ Google, если будет запрос.
3. Подключить папку с фактическими отчётами Sendsay в разделе **Служебное**.
4. Нажать **Синхронизировать всё**.
5. При публикации новой версии выбрать **Развернуть → Управление развертываниями → Изменить → Новая версия → Развернуть**.

`setup()` при каждом обновлении запускать не нужно. Он нужен только для первичной инициализации v2 или если служебное хранилище было удалено.

## Файлы

- `Code.gs` — серверная логика, импорт Sendsay и сборка DEMO;
- `SendsayUpload.gs` — безопасное сохранение ручных загрузок и повтор ошибочных импортов;
- `zz_plan_fix.gs` — временный фикс распознавания недельных планов;
- `zz_calls_ui.gs` — сборка дополнительных UI-модулей в Web App;
- `index.html` — основной интерфейс;
- `sendsay_ui.html` — ручная загрузка отчётов по save-first маршруту;
- `mail_classification_ui.html` — единая финальная классификация типов рассылок;
- `russian_metrics_ui.html` — понятные редакциям русские подписи метрик;
- `email_analytics_ui.html`, `news_ui.html`, `calls_ui.html`, `compat_ui.html`, `runtime_fixes_ui.html`, `final_polish_ui.html` — дополнительные модули интерфейса;
- `Calls.gs` — аналитика звонков;
- `appsscript.json` — манифест Apps Script.

GitHub Pages может использоваться как демонстрационная оболочка. Рабочие данные читаются в Google Apps Script Web App через авторизованный доступ к Google Drive и Google Sheets.
